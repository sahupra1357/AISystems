## How to implement (build order)

1. **Golden set first** (07.1) — before any pipeline code. It defines what "correct" means and gates everything after.
2. **Thin vertical slice**: one connector → one parser → recursive chunking → embeddings → a vector index → simple retrieval → a grounded prompt with citations. Measure on the golden set.
3. **Security from day one**: tenant and ACL capture at ingest (00.1.5), permission-filtered retrieval (10.1). Retrofitting is a re-ingest.
4. **Add the high-ROI quality layers in order**: hybrid search (04.5.1) → reranking (04.5.2) → parent–child chunking (04.1.5) → query rewriting (04.4.1) → abstention (04.5.4).
5. **Add the production layers**: observability (08.6), budgets (03.4, 05.12), guardrails (08.2, 08.3), failure handling (08.7), caching (03.5).
6. **Close the loop**: online signals (07.9) → triage (12.2) → golden cases (12.1) → CI gates (08.1) → canary (09.5).
7. **Only then** consider agents (05.x), advanced RAG (04.6), and fine-tuning (11.x) — each justified by a measured gap.

## Small example — the online path, assembled

```python
def handle_request(raw_query: str, request, cfg) -> dict:
    trace_id = new_trace_id()
    with span("app.request", trace_id=trace_id, **version_vector(cfg)):          # 08.6

        caller = authenticate(request)                                            # 10.1
        guard = input_guardrails(raw_query, caller, policy_for(caller))           # 08.2
        if not guard.allow:
            return refusal(guard.reason, trace_id)

        understanding = understand_query(guard.masked_text, caller, history())    # 04.4.1/.4/.5/.6
        if understanding.route != "vector":
            return HANDLERS[understanding.route](understanding, caller, trace_id) # 04.4.6, 04.6.6

        budget = Budget(max_tokens=cfg["budgets"]["tokens"], max_usd=cfg["budgets"]["usd"],
                        max_seconds=cfg["budgets"]["seconds"])                    # 05.12

        pool = hybrid_retrieve(understanding.query, caller,                        # 04.5.1 (ACL-filtered, 10.1)
                               k=cfg["retrieval"]["pool_k"], filters=understanding.filters)
        ranked = rerank(understanding.query, pool, top_n=cfg["retrieval"]["final_k"])  # 04.5.2
        ranked = mmr_select(ranked, understanding.query_vec, k=cfg["retrieval"]["final_k"])  # 04.5.3

        conf = retrieval_confidence(ranked)                                        # 04.5.4
        if conf["top"] < cfg["thresholds"]["tau_low"]:
            return refuse(RefusalReason.NO_RELEVANT, {...}, trace_id)              # 04.7.5

        parents = collapse_to_parents(ranked)                                      # 04.1.5
        memory = retrieve_memory(caller, understanding.task_type, understanding.query)  # 06.3
        context, meta = assemble(understanding.query, parents, memory, history(),  # 03.1–03.4
                                 budget=cfg["budgets"]["context_tokens"])

        out = generate_grounded(understanding.query, context, budget=budget)       # 02.1, 04.7.1
        out = validate_citations(out, parents)                                     # 04.7.2
        out = faithfulness_gate(out, parents)                                      # 04.7.3
        verdict = output_guardrails(out, parents, caller, policy_for(caller))      # 08.3

        record_outcome(trace_id, out, ranked, meta, budget)                        # 08.6 → 07.9 → 12.1
        audit.record("ai.query_answered", caller, understanding, out, ranked)      # 10.4
        return {"answer": verdict.text, "citations": render_citations(out, parents),
                "trace_id": trace_id, "degraded": out.get("degraded", False)}
```

## Pros

- **Every stage has a named owner, a metric, and a failure mode** — the architecture is also the operations model.
- **Each layer is independently evaluable** (07.7), so problems localise.
- **Offline/online separation** lets ingestion scale independently of serving.
- **The flywheel is part of the architecture**, not an afterthought, which is what makes the system improve.

## Cons

- **It's a lot of machinery** — a naive prototype is five components, this is thirty. Build incrementally against measured gaps.
- **Every stage is a failure point**; without observability the composite is hard to debug.
- **Cost and latency accumulate** across stages; each needs a budget.
- Over-engineering is the common failure: teams build advanced RAG patterns before measuring whether hybrid + rerank suffices.

## When to use

As the map for any document-grounded AI system. Use it to locate what you're building, and what you're missing.

## When NOT to use (all of it)

- A prototype needs the thin slice, not the full diagram.
- Not every system needs agents, graphs, multimodal retrieval, or fine-tuning — each is justified by a measured gap, not by the diagram's completeness.

## Production at scale

**The order of investment is not the order of the diagram.** After a working thin slice, the highest-return additions are consistently: reranking (04.5.2), hybrid search (04.5.1), parent–child chunking (04.1.5), and abstention (04.5.4). Advanced RAG patterns (04.6), agents (05.x), and fine-tuning (11.x) come far later, and only when evals show the specific gap they close.

**Security and versioning cannot be retrofitted cheaply.** ACL capture at ingest (00.1.5) and document versioning (00.1.4) touch every chunk; adding them later means re-ingesting the corpus. Build them into the thin slice.

**Observability is a prerequisite, not a phase.** Without retrieved chunk IDs and scores in the trace (08.6), every debugging session is guesswork and the flywheel cannot start.

**The offline path usually costs more than the online path** in document-heavy systems: parsing, embedding, and contextual enrichment dominate. Change detection (00.1.2) and dedupe (00.1.3) are the largest cost levers most teams haven't pulled (09.1).

**Budgets at every stage**: context tokens (03.4), agent steps and dollars (05.12), per-tenant quotas (09.4). Unbudgeted stages are where cost incidents originate.

**Each stage needs a degraded mode** (08.7): reranker down → fusion order; dense down → BM25; generation down → return sources. The composite availability of ten dependencies without degradation is poor.

**Keep the version vector everywhere** (09.5, 08.6) — it's what makes a thirty-component system debuggable at all.

## Prod checklist

- [ ] Golden set exists before the pipeline
- [ ] Thin vertical slice working end to end, measured
- [ ] ACL capture and document versioning built in from the start
- [ ] Hybrid + rerank + parent–child + abstention added and measured in that order
- [ ] Observability with chunk IDs, scores, and the version vector on every request
- [ ] Budgets at every stage; per-tenant quotas
- [ ] Degraded mode defined for each stage
- [ ] CI eval gates and canary rollout wired
- [ ] Flywheel running: signals → triage → golden cases → fixes
- [ ] Advanced components (agents, graph, multimodal, fine-tuning) justified by measured gaps

## Metrics to watch

| Metric | Why |
|---|---|
| Per-stage latency and cost | Where the budget goes |
| Failure-bucket histogram (12.2) | Which stage to invest in |
| End-to-end quality on the golden set | The headline |
| Degraded-response rate by stage | Composite reliability |
| Ingest cost per 1k documents | The usually-dominant line item |

## Video takeaway (30 seconds)

"Two pipelines and a loop. Offline: ingest with permissions and versions attached, parse per page, chunk with structure, embed, index into vector and keyword stores. Online: authenticate, guard the input, understand and route the query, retrieve hybrid with the caller's permission filter, rerank, assemble a budgeted context, generate with grounding, check citations and faithfulness, guard the output, stream. Then traces and feedback flow into the flywheel. Build the thin slice first and measure it — but put permission capture and document versioning in from day one, because those two are the ones you cannot retrofit without re-ingesting everything you own."
