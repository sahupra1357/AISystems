# 4.3.1 Indexing → Index types: Flat, HNSW, IVF-PQ (and tuning the recall/latency curve)

> **Source:** `AI_System.md` §4.3 Indexing & vector stores
> **Pipeline stage:** embed → **index** → retrieve
> **One-liner:** Flat = exact, fine for small corpora. HNSW = fast approximate search, memory-hungry, the default. IVF-PQ / quantised = large corpora on constrained memory at some recall cost. Tune `ef_search` / `nprobe` to pick your point on the recall-vs-latency curve — and measure recall against a flat index, not against hope.

---

## What it is

Approximate nearest-neighbour (ANN) search trades exactness for speed and memory. The main families:

| Type | How | Memory | Query latency | Recall | Build time | Use |
|---|---|---|---|---|---|---|
| **Flat** (brute force) | Compare the query to every vector | vectors only | O(n); ms up to ~1M with SIMD/GPU | 100% | none | Small corpora; ground truth for measuring ANN recall; rescoring stage |
| **HNSW** | Multi-layer proximity graph; greedy search with beam `ef_search` | vectors + graph (≈ 1.5–2× vectors) | sub-ms to few ms | 95–99.9% tunable | minutes–hours | Default for ≤ ~100M vectors in RAM |
| **IVF** | k-means partitions; search `nprobe` nearest partitions | vectors + centroids | ms | tunable by `nprobe` | fast | Large corpora; pairs with PQ |
| **IVF-PQ / PQ** | Product quantisation compresses vectors 8–64× | tiny | ms | lower unless rescored | needs training | 100M–billions; memory-bound |
| **Scalar quantisation (SQ8 / int8, binary)** | 4× / 32× compression, usable with HNSW | small | fast | small loss; rescoring recovers | fast | Common middle ground |
| **DiskANN / Vamana** | Graph on SSD with in-memory compressed vectors | low RAM | few ms | high | hours | Billion-scale on a few machines |

Two-stage designs are the norm at scale: compressed/truncated ANN (binary, int8, Matryoshka 256d) for candidates → exact rescoring with full vectors from disk for the top few hundred.

**Key parameters**:
- HNSW build: `M` (graph degree, 16–64; memory ↑, recall ↑), `ef_construction` (100–500; build time ↑, quality ↑). Query: `ef_search` (top-k ≤ ef ≤ ~500; recall ↑, latency ↑).
- IVF: `nlist` (partitions, ~√n to 4√n), `nprobe` (1–10% of nlist).
- PQ: `m` subvectors, `nbits`; more = better recall, more memory.

## How to implement

1. **Measure corpus size and growth**; pick a family from the table; plan for 3–5× growth.
2. **Build a flat index on a sample** (or full corpus if feasible) as the recall reference.
3. **Build the ANN index**; sweep the query parameter (`ef_search` / `nprobe`) and record recall@k (vs flat) and p95 latency at production concurrency; choose the knee of the curve (often recall@10 ≈ 0.97–0.99).
4. **Filtered search** changes everything (04.3.3): re-run the sweep with realistic filters (tenant, current version).
5. **Set params in config**; version them; monitor recall with a canary set.
6. **Plan updates/deletes**: HNSW deletes are tombstones; schedule compaction; IVF needs periodic re-training of centroids as the distribution drifts.
7. **Capacity**: memory = n × (d × bytes + graph); replicas for QPS and HA; shards by tenant or hash.

## Small example

```python
import faiss, numpy as np, time

d = 1024
xb = np.load("doc_vecs.npy").astype("float32"); faiss.normalize_L2(xb)
xq = np.load("golden_query_vecs.npy").astype("float32"); faiss.normalize_L2(xq)

flat = faiss.IndexFlatIP(d); flat.add(xb)
_, gt = flat.search(xq, 10)                                   # ground truth top-10

hnsw = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)  # M=32
hnsw.hnsw.efConstruction = 200; hnsw.add(xb)

def recall_at_10(I): return float(np.mean([len(set(I[i]) & set(gt[i])) / 10 for i in range(len(xq))]))

for ef in (16, 32, 64, 128, 256):
    hnsw.hnsw.efSearch = ef
    t0 = time.time(); _, I = hnsw.search(xq, 10); dt = (time.time() - t0) / len(xq) * 1000
    print(f"ef_search={ef:3d} recall@10={recall_at_10(I):.3f} latency={dt:.2f} ms/query")

# IVF-PQ for memory-constrained scale
nlist = int(4 * np.sqrt(len(xb)))
quant = faiss.IndexFlatIP(d)
ivfpq = faiss.IndexIVFPQ(quant, d, nlist, 64, 8, faiss.METRIC_INNER_PRODUCT)   # m=64 subvectors, 8 bits
ivfpq.train(xb[:200_000]); ivfpq.add(xb)
for nprobe in (8, 32, 128):
    ivfpq.nprobe = nprobe; _, I = ivfpq.search(xq, 10)
    print(f"nprobe={nprobe:3d} recall@10={recall_at_10(I):.3f}  bytes/vec≈{64}")
```

## Pros

- **HNSW**: excellent recall/latency; incremental inserts; widely supported (pgvector, Qdrant, Weaviate, Milvus, Elasticsearch/OpenSearch, Vespa, Redis).
- **IVF-PQ / quantisation**: fits 10–100× more vectors in the same memory; cheap at scale.
- **Flat**: exact, simple, the yardstick; great on GPU for < few million.
- Two-stage (compressed → rescore) gets most of the memory saving with little recall loss.

## Cons

- **HNSW memory** is RAM-resident; billions of 1024d vectors is many hundreds of GB.
- **Deletes/updates** degrade HNSW (tombstones) until compaction; IVF centroids drift.
- **PQ recall loss** on hard queries; rescoring needs full vectors somewhere (disk).
- **Parameter tuning** is corpus-specific and interacts with filtering.
- Build times for large HNSW indexes are hours; re-index windows (04.2.4) must account for it.

## When to use

- **Flat**: < ~1M vectors, or as ground truth, or as the rescore stage.
- **HNSW**: the default for most production RAG (≤ tens of millions per shard).
- **IVF-PQ / SQ / DiskANN**: hundreds of millions+ or strict memory budgets.
- **Two-stage**: large corpora where recall matters — compressed ANN + exact rescore.

## When NOT to use

- HNSW for billion-scale on a single node — it won't fit; shard or go disk-based.
- PQ without rescoring on precision-critical retrieval (legal/medical): recall loss shows up as missed answers.
- Flat for latency-critical paths over large corpora.

## Production at scale

**Measure recall against flat, always.** ANN recall is silent: the index returns *something* fast. Keep a golden query set with flat-index ground truth; run it daily; alert on recall drops (after compaction, after parameter changes, after distribution shift).

**Filtering dominates tuning.** With a tenant filter selecting 1% of vectors, HNSW at default `ef` may return few or zero results (04.3.3). Tune with real filters; use stores with filter-aware graph traversal; or partition by tenant.

**Sharding and replicas.** Shard by tenant (isolation, easy deletes) or by hash (balance); replicate for QPS and HA. Query fan-out across shards + merge adds latency; keep shard count modest.

**Memory math** (HNSW, float32): `n × d × 4` for vectors + `n × M × 2 × 4`–ish for graph. 20M × 1024d ≈ 82 GB + ~5 GB graph. With int8 SQ: ~25 GB. With binary + rescore: ~3 GB + full vectors on disk.

**Updates**: batch inserts; schedule compaction/optimizer runs; watch tombstone ratio (00.1.4); rebuild segments beyond ~20–30% deleted.

**IVF drift**: retrain centroids when the corpus grows >2× or the domain mix changes; a migration-style rebuild (04.2.4).

**Warm-up and page cache**: after restarts, HNSW graphs need to be in memory; pre-warm replicas before routing traffic; disk-based indexes need SSDs and page-cache sizing.

**Observability**: p50/p95 latency per shard, recall canary, memory per shard, tombstone ratio, `ef`/`nprobe` in effect, queue depth on ingestion writes.

**Managed stores** hide these knobs behind defaults; still run the recall canary — defaults are tuned for their benchmarks, not your filters.

## Prod checklist

- [ ] Index family chosen by size/memory/latency; growth planned

## Video takeaway (30 seconds)

"Three index families. Flat compares your query to every vector — exact, fine up to about a million, and the yardstick for everything else. HNSW is a graph you walk greedily — fast, near-exact, and the default, but it lives entirely in RAM. IVF with product quantisation compresses vectors ten to sixty times for hundreds of millions of vectors, at some recall cost you win back by rescoring the top few hundred exactly. Whatever you pick, tune ef-search or nprobe against a flat index with your real tenant filters on — and run that recall check every day, because approximate search fails silently."
