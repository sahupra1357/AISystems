# 15.1 Common failure modes (and the fix)

> **Source:** `AI_System.md` §15 Common failure modes
> **Pipeline stage:** diagnosis
> **One-liner:** Eight symptoms, their usual cause, and the fix. Use it as a lookup when something is wrong — most production AI failures are one of these, and each has a known remedy.

---

## What it is

| Symptom | Usual cause | Fix | Files |
|---|---|---|---|
| **Right doc exists, never retrieved** | Chunk lacks context/keywords; dense-only search | Hybrid + contextual retrieval + query rewriting | 04.5.1, 04.1.6, 04.4.1 |
| **Answer cites the wrong section** | Chunks too large, no reranking | Parent–child + cross-encoder rerank | 04.1.5, 04.5.2 |
| **Confidently wrong on a fresh question** | No abstention path | Score threshold + faithfulness check | 04.5.4, 04.7.3 |
| **Correct at turn 1, wrong at turn 3** | No query rewriting over history | Coreference-resolving rewrite step | 04.4.1, 03.2 |
| **Costs 10× the estimate** | No caching, top-k too large, agent loops | Prompt cache, rerank-then-trim, step budgets | 03.5, 04.5.2, 05.12 |
| **Works in dev, fails in prod** | Eval set isn't representative | Sample real traffic into the golden set | 07.1, 07.9, 12.1 |
| **Table questions always wrong** | Table flattened at parse time | Structure-preserving parser, table-aware chunks | 00.3.2, 00.2.3, 04.1.3 |
| **Agent takes a destructive action** | Excessive agency + injection | Least-privilege tokens, HITL gate, data≠instructions | 08.5, 05.8, 08.4 |

Four more that recur often enough to add:

| Symptom | Usual cause | Fix | Files |
|---|---|---|---|
| **Answers a superseded policy** | Old versions still retrievable | Version filter + `is_current` on every query | 00.1.4, 04.7.4 |
| **Top-5 results are five copies of one paragraph** | No dedupe; chunk overlap | Exact/near dedupe at ingest + MMR at query time | 00.1.3, 04.5.3 |
| **Refuses things it clearly knows** | Threshold too strict; over-grounded prompt | Recalibrate τ; measure false-refusal rate | 04.5.4, 04.7.1 |
| **Quality dropped and nobody knows why** | No version vector in traces; unpinned model | Version-stamped traces; pin models | 08.6, 09.5 |

## How to implement (the diagnosis workflow)

1. **Reproduce with the trace** (08.6): the query, the caller, the retrieved chunk IDs and scores, the version vector.
2. **Run the diagnostic ladder** (07.7) to find the first failing stage — this maps directly to a row above.
3. **Confirm with a second case** of the same shape; a single instance can be an outlier.
4. **Check the version vector**: did anything change (prompt, model, index, parser) around when it started?
5. **Apply the fix at the identified stage**, not at the stage where the symptom appeared.
6. **Add the case to the golden set** and confirm it fails before the fix and passes after (12.1).
7. **Check whether the same cause explains other open failures** — most of these are systemic, not isolated.

## Small example

```python
SYMPTOM_PLAYBOOK = {
    "right_doc_never_retrieved": {
        "check": lambda t: t["expected_chunk_ids"] and not set(t["expected_chunk_ids"]) & set(t["pool_ids"]),
        "diagnostics": ["is the query identifier-heavy? → is BM25 in the mix (04.5.1)",
                        "do the chunks carry breadcrumbs/context headers? (04.1.3, 04.1.6)",
                        "was the query a pronoun-laden follow-up? (04.4.1)",
                        "did an ACL or date filter exclude it? (04.3.3, 04.4.5)"],
        "fix_order": ["hybrid search", "contextual retrieval", "query rewriting", "embedding fine-tune"],
    },
    "cites_wrong_section": {
        "check": lambda t: t["expected_chunk_ids"] and set(t["expected_chunk_ids"]) & set(t["pool_ids"])
                           and not set(t["expected_chunk_ids"]) & set(t["final_ids"]),
        "diagnostics": ["is a cross-encoder reranker in place? (04.5.2)",
                        "are chunks too large to be precise? (04.1.5)"],
        "fix_order": ["add reranking", "parent-child chunking", "reduce child chunk size"],
    },
    "confidently_wrong_fresh_question": {
        "check": lambda t: t.get("retrieval_top_score", 1) < 0.35 and not t.get("abstained"),
        "diagnostics": ["is there a score threshold? (04.5.4)",
                        "is there a faithfulness gate? (04.7.3)",
                        "does the golden set contain unanswerable questions? (07.1)"],
        "fix_order": ["score threshold + abstention", "faithfulness gate", "grounded prompt rules"],
    },
    "cost_blowup": {
        "check": lambda t: t["cost_usd"] > 10 * MEDIAN_COST,
        "diagnostics": ["cache hit rate on this call site? (03.5)",
                        "how many chunks entered the context? (04.5.2, 03.4)",
                        "agent step count and budget? (05.12)",
                        "escalation rate to the reasoning tier? (01.2)"],
        "fix_order": ["prompt caching", "rerank-then-trim", "step/token budgets", "routing thresholds"],
    },
    "destructive_agent_action": {
        "check": lambda t: any(a["writes"] and not a.get("approved") for a in t.get("actions", [])),
        "diagnostics": ["does the caller's role even permit this tool? (08.5)",
                        "was flagged content in context? (08.4)",
                        "is there an approval gate for this tool? (05.8)"],
        "fix_order": ["remove the tool from the role", "tainted-context suppression", "approval gate"],
        "severity": "critical",
    },
}

def diagnose(trace) -> list[dict]:
    """Match a failing trace against the playbook; ordered by confidence."""
    matches = []
    for name, spec in SYMPTOM_PLAYBOOK.items():
        try:
            if spec["check"](trace):
                matches.append({"symptom": name, "diagnostics": spec["diagnostics"],
                                "fix_order": spec["fix_order"],
                                "severity": spec.get("severity", "normal")})
        except (KeyError, TypeError):
            continue
    return sorted(matches, key=lambda m: 0 if m["severity"] == "critical" else 1)

def systemic_check(symptom: str, window_days=7) -> dict:
    """Is this one bug or a class? Almost always a class."""
    traces = failing_traces(window_days)
    matching = [t for t in traces if SYMPTOM_PLAYBOOK[symptom]["check"](t)]
    return {"count": len(matching), "share": len(matching) / max(len(traces), 1),
            "concentrated_in": Counter(t["source"] for t in matching).most_common(3),
            "verdict": "systemic" if len(matching) / max(len(traces), 1) > 0.15 else "isolated"}
```

## Pros

- **Fast diagnosis**: a symptom lookup turns hours of investigation into minutes.
- **Prevents fixing the wrong layer** — the most common waste in AI projects is prompt-tuning a retrieval bug.
- **Shared vocabulary** across a team, and a natural onboarding document.
- Each row links to a tested remedy rather than a general principle.

## Cons

- **Symptoms overlap**: "wrong answer" can match several rows; the ladder (07.7) disambiguates, the table alone does not.
- **Playbook thinking can stop investigation early** on a genuinely novel failure.
- **Fixes have costs**: reranking adds latency, parent–child adds complexity — the table names the remedy, not the trade-off.
- Needs trace data to apply; without chunk IDs and scores, most checks can't run (08.6).

## When to use

Whenever something is wrong — as the first lookup after reproducing with a trace. Also as a design checklist: a system with none of these mitigations will exhibit most of these symptoms.

## When NOT to use

- As a substitute for the diagnostic ladder when the symptom is ambiguous.
- For novel or safety-critical failures, where a full investigation is warranted regardless of pattern match.

## Production at scale

**Most of these are systemic, not isolated.** When one appears, run the systemic check: how many of the last week's failures share it, and are they concentrated in one source, tenant, or document type? Fixing the class is usually one change; fixing instances is endless (12.2).

**Two of these are prevention, not diagnosis.** "Agent takes a destructive action" and "answers a superseded policy" should be structurally impossible — least-privilege credentials (08.5) and version filtering (00.1.4) — rather than symptoms you fix after they occur.

**"Works in dev, fails in prod" is an eval-set problem**, and the fix is the flywheel (12.1): continuous sampling of real traffic into the golden set. If this symptom recurs, the loop isn't running.

**"Quality dropped and nobody knows why" is an observability problem.** The version vector on every trace (08.6) and pinned models (09.5) turn it into a five-minute bisection.

**Cost blowups have four common causes** in this order: cache hit rate collapse (a variable in the prompt prefix, 03.5), top-k too large (04.5.2), unbounded agent loops (05.12), and over-escalation to the reasoning tier (01.2). Check them in that order.

**Track symptom frequency over time** as a companion to the failure-bucket histogram (12.2) — it shows which mitigations have landed.

**Add your own rows.** Every domain develops its own recurring failures; the table is a starting set, not a closed list, and extending it is how team knowledge accumulates.

## Prod checklist

- [ ] Trace-based reproduction available for any reported failure (chunk IDs, scores, version vector)
- [ ] Diagnostic ladder run before applying a fix
- [ ] Systemic check performed: is this a class or an instance?
- [ ] Fix applied at the diagnosed stage, not the symptom stage
- [ ] Case added to the golden set; fails before, passes after
- [ ] Structural preventions in place for the two critical rows (least privilege, version filtering)
- [ ] Symptom frequency tracked over time
- [ ] Playbook extended with domain-specific failures as they're found

## Metrics to watch

| Metric | Why |
|---|---|
| Symptom frequency by type over time | Which mitigations have landed |
| Systemic vs isolated ratio | Whether you're fixing classes or instances |
| Median time from report to diagnosis | Observability effectiveness |
| Recurrence of previously-fixed symptoms | Durability of fixes |
